# 下游批量同步：待 Review 的需求与设计边界

## 用户目标

- 手动维护一份配置清单，定位依赖 AGENTS Core 的待更新下游仓库。
- 每个目标仓库对应 Subtask，通过 Orca 并行 Agent 执行。
- 在任意已接入的下游仓库发起同一批次更新，不必逐个进入目标仓库。
- 更新契约来自 README“Core 更新后同步已有项目”一节，不另造覆盖式 updater。
- 当前阶段仅需求 Review 与方案设计；不编码、不 fetch、不修改下游、不启动 workers。

## 已核对 README 的约束

- 使用已认证 Git 刷新 Core，固定 origin/main 完整 SHA；失败停止，不回退缓存。
- 系统级受管块 dry-run 与项目级 base/ours/theirs 语义比较合并展示；无冲突也需明确 Review，批准可按部分范围授权。
- 输入变化需重新预览与 Review；不自动删除、覆盖项目专属内容或把初始化器作为已有项目更新命令。
- 按 COPY_MAP 更新已登记文件；完成合并和验证后更新 manifest 基线。不得复制 Core 自用 Task 实例。
- 不自动暂存、提交、推送；保留验证结果与采用/保留/拒绝的变化。

## 初步设计方向，尚待确认

- 新增专门批量同步入口，复用 task-runtime 和 task-orchestration。配置描述仓库目标，不保存凭据或任意可执行命令。
- 共享配置可从各下游定位；私有绝对路径放本机配置，版本化模板用占位示例。入口必须解决旧下游未安装新 Skill 的引导问题。
- 协调者一次冻结本轮 Core SHA，各项目 worker 比较同一 theirs，各自 base 取自身 manifest。
- 系统级按实际主机/客户端目标去重，由协调者统一预览与应用，项目 worker 不并发写同一系统文件。
- 先展示中文执行树并获得编排批准；项目并行预览后汇总一份系统级+项目级更新提案。用户批准具体变化后，仅授权的项目并行应用与验证。
- 编排方案 Review 与具体更新内容 Review 是不同确认对象；已有明确批准不重复询问同一对象。
- Task 与计划归属在批次开始时固定，不能因启动入口变化而丢失记录；每仓库状态、Orca 实例、提案、批准和验证可追溯。
- 部分失败独立报告，不把批次整体伪装成成功；未批准、输入变化、失败的仓库不静默应用。

## 待设计/确认

- 首版仅同机本地仓库，还是也要覆盖 SSH/远程环境；不能将远端路径当成本地路径。
- 配置清单的共享位置、定位规则、启用/分组选择和默认是否包含发起仓库。
- 启动入口与协调 Task 的固定归属；旧下游没有新 Skill 时怎样可复现地引导。
- Agent 默认、并发上限、同系统级目标的更新先后顺序及失败恢复规则。
- 新 Skill 的安装映射需要在实现时更新 COPY_MAP，已有上轮编排 Skill 仍未进入当前安装清单。

## 已确认补充：按环境独立发起

- 用户分别在本地和 SSH 环境发起两次更新；不设计单次跨主机扇出批次。
- 每个执行环境有独立配置、目标 repo 集合、Core 检出、系统级目标及批次状态。配置中的路径按目标环境自身解释；Orca 必须绑定当前执行环境的真实标识，不得混用本机路径或 local shell。
- 默认更新当前环境清单中全部 enabled 仓库；发起仓库在清单且 enabled 时同样参与，不因其为当前工作区而排除，也不把未登记的发起仓库自动加入。允许指定子集。
- 可从同一环境任一下游项目发起。是否已安装新 Skill 不应成为无法更新的循环依赖，需提供指向共享可信 Core 入口的引导。

## 具体方案建议，待 Review

- 新增 core-sync Skill，复用 Task Runtime 与 task-orchestration，按固定 SHA 的 README 更新协议执行；不将任意 shell 命令放进清单。
- 每环境维护一份用户级私有 JSON 清单，建议 ~/.config/agents-core/repos.json；显式配置路径可覆盖默认。包含 schema、Core 检出定位、默认 Agent/并发设置、repo 的稳定 id/path/enabled。可选标签与分组选取后续按需。
- config 路径、repo 路径与实际 Core 检出在批次准备时规范化和去重，路径错误、重复目录、非受管项目独立报告；不自动克隆或首次初始化。
- 批次控制状态建议放当前环境独立的共享控制工作区，避免 Task 记录写入 Core 源检出导致 dirty、污染固定提交基线，也避免 Task 归属依赖发起仓库。控制工作区的一次性建立与所需工具安装须单独设计并 Review。
- 目标目录由清单决定，入口 cwd 仅用于确定环境和展示发起上下文。SSH 下配置读取、Core fetch、Task 状态和所有 worker 均应在该环境执行；本地仅为 Orca 交互端时不能读取本地清单冒充远端目标。
- 协调者在准备阶段固定本轮 Core 完整 SHA；项目预览并行，各项目自己的 manifest source_commit 为 base。系统级按实际目标文件去重、集中预览和应用。
- 两阶段：全部项目预览完成/明确阻塞后汇总 Review；用户可批准部分系统级/项目级提案；随后仅获批且输入未变化的目标并行应用/验证。同一 repo 使用同一 Subtask 分阶段续跑，优先复用已有 Orca 实例。
- 更新系统级目标时先处理共享部分，再启动依赖它的项目应用；若仅批准项目部分且可独立进行，不强制更新系统级目标。对实际依赖明确阻塞，不扩大授权。
- 已同步至目标且验证通过的 repo 标记无需变更；失败目标不静默回退、重试覆盖、提交或推送。新 Skill 与编排 Skill 的 COPY_MAP 安装登记属于后续实现范围。
